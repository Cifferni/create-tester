# tester 使用说明

AI 驱动页面测试:测试人员只描述测试目标、放用例,AI harness(Codex / opencode / Claude 等)通过 MCP 读用例、写用例、跑测试、判失败。执行层是原生 Playwright。

## 一、建项目

```bash
npm create tester@latest          # 交互式
npm create tester@latest my-test -b chromium --no-install   # 非交互
cd my-test && npm install
```

生成的项目只有:`test-cases/`、`playwright.config.ts`、`tests/`、脚本。没有自定义配置文件,配置走环境变量。

## 二、接入 AI harness(MCP)

MCP server 就是工程内 `mcp/server.cjs`,在 AI harness(Codex / opencode / Claude Code 等)的 MCP 配置里加一个 stdio server:

```json
{
  "mcpServers": {
    "tester": {
      "command": "node",
      "args": ["D:/my-test/mcp/server.cjs"],
      "cwd": "D:/my-test"
    }
  }
}
```

> `args` 里的路径换成你的工程根目录;`cwd` 指向工程根目录(工具按它读 `test-cases/`、`tests/`、`result/`)。也可在工程根目录直接跑 `node mcp/server.cjs` 手动验证。

配好后,对 AI 说的话就是需求描述,例如:

> "把 test-cases/登录.xlsx 转成测试用例跑一遍,失败的给我分析根因"
> "给订单功能写几个测试,断言接口 /api/order 返回 code=0"

AI 会通过 MCP 工具自动完成:读用例(`convert_case`)→ 看页面(`snapshot`)→ 写 `tests/*.spec.ts` → 跑测试(`run_tests`)→ 分析失败(`failures`)。

## 三、MCP 工具一览

| 工具 | 作用 |
| --- | --- |
| `list_cases` | 列出 `test-cases/` 下的用例文件 |
| `convert_case` | 用例文件(xlsx/xmind/csv/md/txt)→ 结构化文本 |
| `snapshot` | 打开被测页面,返回可交互结构快照(纯图标按钮补充 class/title) |
| `inspect` | 只读探查 DOM:按选择器返回 outerHTML/属性(不改数据) |
| `list_specs` | 列出 `tests/` 下已生成的 spec |
| `run_tests` | 后台跑测试,立即返回"运行中",用 `status`/`failures` 轮询(不做同步等待,避免客户端超时) |
| `status` | 读报告,返回通过/失败/跳过/耗时总览 |
| `failures` | 读报告,返回全貌 + 失败详情(含 stdout/stderr 日志) |
| `retry_failed` | 只重跑上次失败的 spec |
| `generate_spec` | 按 test-cases/ 用例生成 spec 骨架(含 apiRecorder 模板) |

## 四、用例输入(test-cases/,零重写)

测试人员把既有用例放进 `test-cases/`,支持:

- `Markdown`(.md)— 需求/用例文档,表格自动转规整文本
- `Excel`(.xlsx / .xls)— 大批量用例管理
- `XMind`(.xmind)— 梳理测试点/场景
- `.csv` — 禅道 / TestLink / Jira 导出
- `.txt` — 自然语言操作步骤

**不需要改写成任何特定格式**,AI 通过 `convert_case` 读取后自动理解。

## 五、运行与回归

```bash
npm run test        # playwright test:并行、重试、失败自动截图+trace
npm run test:headed # 带界面执行
```

报告:`result/report/index.html`(HTML,失败带截图与 trace,可直接当 bug 证据)。

## 六、接口自动断言(核心差异化)

不用手写 `waitForResponse`。先开捕获器,再断言:

```ts
import { test, expect } from '@playwright/test';
import { apiRecorder, expectApi } from '../mcp/api.cjs';

test('登录后校验接口', async ({ page }) => {
  const api = apiRecorder(page);
  await page.goto('/login');
  await page.getByTestId('username').fill('test01');
  await page.getByTestId('login-submit').click();

  await expectApi(api, '/api/login').code('0');                       // 业务码
  await expectApi(api, '/api/login').field('data.token').notEmpty();  // 字段
  await expectApi(api, '/api/login').status(200);                     // 状态码
});
```

断言找不到接口会等最多 15 秒;状态码 ≥400 默认直接失败。

## 七、定位策略(测试人员不用懂,但知道规则更稳)

| 优先级 | 方式 | 例子 | 谁来保证 |
| --- | --- | --- | --- |
| 1 | `data-testid`(最稳) | `getByTestId('login-submit')` | 开发在关键元素埋点 |
| 2 | 语义定位 | `getByRole('button', { name: '登录' })` | AI 生成 |
| 3 | CSS / XPath | `#loginBtn` | 兜底 |

建议团队约定:开发在关键交互元素上加 `data-testid`(`kebab-case` 语义命名),AI 会优先用它,测试最稳定。

## 八、配置(环境变量)

| 环境变量 | 说明 |
| --- | --- |
| `BASE_URL` | 被测页面地址(默认 `http://localhost:3000`) |
| `TESTER_BROWSER` | 浏览器:chromium / chrome / firefox / webkit |

也可直接改 `playwright.config.ts`(被测地址/浏览器/报告/重试次数都在这里)。

## 常见问题

- **页面打开失败**:检查 `playwright.config.ts` 的 `use.baseURL` 或 `BASE_URL`;内网系统先连 VPN/内网。
- **AI 生成时定位不到元素**:优先确保被测页面可达;页面结构越语义化(按钮有文字、输入框有 placeholder)定位越准;关键元素让开发加 `data-testid`。
- **断言接口报"未捕获到接口"**:确认操作确实触发了该请求(URL 关键字是否匹配);接口慢时 `expectApi` 会自动等 15 秒。
- **看不到接口记录**:默认跳过 js/css/图片等静态资源,只记录接口。
- **失败用例想重试**:改 `playwright.config.ts` 的 `retries`。

## 目录结构

```
test-cases/         测试人员的既有用例(输入源)
tests/<功能>/*.spec.ts  可执行用例,按功能模块组织(AI 生成 或 codegen 录制)
playwright.config.ts  Playwright 配置
result/             所有输出:report/(HTML 报告)、test-results.json、output/(截图/trace)
```
